# cmder-nvm 🚀
> Portable Node.js version management inside Cmder, without Admin privileges.
> Now supports **Windows** and **Linux**.

![[GitHub Release](https://img.shields.io/github/v/release/kbaraniak/cmder-nvm)](https://github.com/kbaraniak/cmder-nvm/releases/latest)

---

## Quick start

**Windows** — download the release, unzip it, double-click `SETUP.cmd`.

That is the whole flow. `SETUP.cmd` unpacks the distribution, verifies Cmder and
nvm-windows against a checksum manifest, installs the first-run hook and opens
Cmder, which then installs Node.js. **No network access is required for the
bootstrap**; only fetching a specific Node.js version needs one.

Working from a checkout? Run `SETUP.cmd` there too — it unpacks Cmder from
`lib/cmder-<version>.zip` into the working tree and leaves `git status` clean.

**Linux** —

```sh
git clone https://github.com/kbaraniak/cmder-nvm.git
cd cmder-nvm
./oobe.sh --node lts --yes
```

## Design

The project is a thin integration layer, not a Node.js manager. It bundles two
artifacts, wires them together, and stays out of the way:

```
cmder-nvm              integration, this project
├── Cmder             terminal, bundled artifact
├── nvm-windows       version manager, bundled artifact
└── Node.js           runtime, managed by nvm-windows
```

`nvm list`, `nvm install 22` and `nvm use 22` keep working exactly as they do
in a normal nvm-windows installation. cmder-nvm does not replace them.

### The repository is source only

Cmder is **not** vendored in the tree. It ships as a single verified archive:

```
cmder-nvm/                 source, ~20 MB
├── SETUP.cmd              the only script a user runs
├── install.cmd
├── doctor.cmd
├── pack.cmd
├── VERSION                cmder-nvm version
├── manifest.json          pinned artifact versions and digests
├── bin/                   nvm-windows and the thin wrappers
├── lib/
│   ├── manifest.cmd       the only reader of VERSION and manifest.json
│   ├── cmder-1.3.24.236.zip    ← Cmder, as an artifact
│   └── oobe/              Linux backend
├── src/profile.d/         the first-run hook
└── tests/
```

After `SETUP.cmd` runs, the same folder also holds the unpacked runtime:

```
cmder-nvm/
├── lib/cmder-1.3.24.236.zip
├── bin/
├── src/
├── Cmder.exe              ← generated
├── vendor/                ← generated
├── config/                ← generated
├── opt/  icons/           ← generated
├── nodejs/  node/         ← generated by install.cmd
```

Everything marked *generated* is in `.gitignore`. Consequences worth stating
plainly:

- **Updating Cmder is one file plus one digest**, not a diff over 330 files.
- **`git status` stays clean** after running `SETUP.cmd` in a checkout.
- **The repository is not smaller.** The archive is 12 MB and `.git` still
  holds the history of the old tree. Shrinking it means rewriting history
  (`git filter-repo`), which is a separate, deliberate decision.

### Deterministic bootstrap

Nothing is downloaded. Both artifacts are bundled and verified against
`manifest.json` before anything is executed:

```
SETUP ─ verify lib/cmder-*.zip  ─ SHA-256 ─ mismatch ? stop : unpack
      ─ verify Cmder.exe        ─ SHA-256 ─ mismatch ? stop
      ─ verify bin\nvm.exe      ─ SHA-256 ─ mismatch ? stop
      ─ install hook ─ launch
```

nvm-windows in particular is never fetched at install time: upstream no longer
publishes the portable archive, and a binary downloaded during setup would make
the installation non-reproducible anyway.

### Versions live in one place

There is exactly one source of truth for the integration version, and it is the
`VERSION` file:

| File | Holds |
| :--- | :--- |
| `VERSION` | cmder-nvm version — read by `pack.cmd`, `install.cmd`, `doctor.cmd` |
| `manifest.json` | pinned Cmder and nvm-windows versions and SHA-256 digests |
| `bin/nvm.exe` | nvm-windows version, reported by `doctor.cmd` |

```
VERSION            ->  cmder-nvm-v2.3.0.zip, the setup banner
manifest.json      ->  Cmder 1.3.24.236, nvm-windows 1.1.10
```

These are independent on purpose: updating Cmder is a new archive plus a new
digest, not a new release of this project.

### The install does not touch your configuration

Cmder runs every `*.cmd` in `%CMDER_ROOT%\config\profile.d` on shell start, and
that directory is already on `PATH` by the time it runs. The first-run hook
therefore lives in `src/profile.d/cmder-nvm.cmd` and is **copied** into
`config/profile.d/` by `SETUP.cmd`.

`config/user_profile.cmd` is never read, written or modified by this project.
Because `config/` is generated, the hook cannot live there in version control —
hence `src/`.

### Install and activate are separate

```bat
install.cmd --node 22 --no-activate   REM fetch and unpack a version
use\node 22                           REM switch to it
```

`install.cmd` installs and, unless `--no-activate` is given, switches to the
version it just installed. Both steps go through the same thin wrappers, so
there is one implementation of each.

## 📦 Platform Support

| Platform | Entry point | Version manager |
| :--- | :--- | :--- |
| Windows (Cmder) | `SETUP.cmd`, then `install.cmd` | nvm-windows (bundled in `bin/`) |
| Linux | `./oobe.sh` | nvm-sh (downloaded into `.nvm/`) |
| macOS | — | not supported; install [nvm-sh](https://github.com/nvm-sh/nvm) manually |

## 🛠️ Usage

### 1. Installation

#### Windows (Cmder)

| Command | Description |
| :--- | :--- |
| `SETUP.cmd` | Unpack a release, verify, and launch Cmder |
| `install.cmd` | Interactive version menu (first run) |
| `install.cmd --node 22` | Install a specific version |
| `install.cmd --node lts` | Install the latest LTS |
| `install.cmd --node lts --yes` | Non-interactive, for CI and machine provisioning |
| `install.cmd --node 22 --no-activate` | Install without switching to it |
| `install\node_js {VER}` | Install a version without the bootstrap |
| `doctor.cmd` | Report the state of the installation |

Versions may be a major line, a full version, or a keyword:

| Command | Resolves to |
| :--- | :--- |
| `install\node_js 18` | Latest v18 release |
| `install\node_js 18.19.0` | That exact version |
| `install\node_js lts` | Latest LTS |
| `install\node_js latest` | Latest release |

#### Linux

| Command | Description |
| :--- | :--- |
| `./oobe.sh` | Full setup, then pick a version from the menu |
| `./oobe.sh 20` | Install a specific version |
| `./oobe.sh --node lts` | Name the version explicitly |
| `./oobe.sh --node lts --yes` | No prompting, for CI |
| `./oobe.sh --check` | Verify the system without installing Node.js |
| `nvm install 20` | Install another version |
| `nvm use 20` | Switch versions |
| `nvm ls` | List installed versions |

Options: `-h/--help`, `-c/--check`, `-q/--quiet`, `-n/--no-menu`, `-y/--yes`,
`--node <version>`. A version can also come from `CMDER_NVM_VERSION`.

After the first run, activate Node.js in the current shell:

```sh
. ./config/user_profile.sh
```

To make it permanent, add that line to `~/.bashrc` (or `~/.zshrc`).

### 2. Switching versions

| Command | Description |
| :--- | :--- |
| `use\node 20` | Switch to Node.js v20 |
| `use\node lts` | Switch to the latest LTS |
| `use\node {VER}` | Switch to any installed version |
| `nvm use 20` | Same, via nvm-windows directly |

`use\node` accepts `lts` and `latest` as well as exact versions; it resolves the
keyword to the matching folder before switching.

### 3. Diagnosing a problem

`doctor.cmd` reports the state of the installation. Every line is `[OK]`,
`[WARN]` or `[FAIL]` with the value that was checked, so a problem is visible
without reading any script:

```text
  cmder-nvm doctor
  ================

  install: C:\Tools\cmder-nvm

  Platform
    [OK]   Windows architecture = x64

  Binaries
    [OK]   Cmder.exe present
    [OK]   bin\nvm.exe present
    [OK]   cmder.sha256
    [OK]   nvm-windows.sha256
    [OK]   nvm.exe version = v1.1.10

  nvm layout
    [OK]   NVM_HOME exists
    [OK]   NVM_HOME = C:\Tools\cmder-nvm\nodejs
    [OK]   NVM_SYMLINK resolves: C:\Tools\cmder-nvm\node
    [OK]   settings.txt present
    [OK]   settings.txt root matches this installation
    [OK]   settings.txt path matches this installation
    [OK]   settings.txt arch = 64
    [OK]   NVM_SYMLINK points inside this installation

  Node.js
    [OK]   installed: v22.14.0
```

A failing check names the cause. For example, a `settings.txt` left behind by a
different installation:

```text
    [FAIL] settings.txt root does not match this installation
              expected C:\Tools\cmder-nvm\nodejs
              actual   C:\Program Files\nvm\nodejs
```

Exit code is `0` when nothing failed and `1` when at least one check failed, so
`doctor.cmd` can gate a script.

## 📦 Building a release

```bat
pack.cmd
```

Reads `VERSION`, verifies `bin\nvm.exe` and the Cmder archive against
`manifest.json`, and refuses to pack if either fails. Stages `bin\`, `lib\`,
`src\` and the top-level scripts, then writes `cmder-nvm-v<VERSION>.zip`.
Development-only files (`.git`, caches, an already-unpacked `nodejs\`) are
excluded.

`vendor\`, `config\`, `opt\` and `icons\` are deliberately **not** staged: they
are produced by `SETUP.cmd` from the archive in `lib\`, so staging them would
ship the payload twice. `lib\` is required for two reasons — `SETUP.cmd` reads
`manifest.json` through `lib\manifest.cmd`, and `oobe.sh` sources `lib\oobe\*.sh`
at runtime, so a Windows-only payload would silently break the Linux flow.

### Updating Cmder

1. Build `lib/cmder-<new-version>.zip` with the new tree, rooted so `Cmder.exe`
   sits at the top level.
2. Put its digest in `manifest.json` under `cmder.archive.sha256`, update
   `cmder.version`, and repoint `cmder.archive`.
3. Update `cmder.sha256` if `Cmder.exe` itself changed.
4. Run `python3 tests/static_checks.py` — it verifies the archive digest and
   hashes `Cmder.exe` straight out of the archive, so a stale manifest is caught
   without unpacking anything.

`VERSION` does not need to change: Cmder is a dependency, not a new release of
this project.

## 🧪 Tests

Two layers, because they answer different questions.

**Static checks** — run anywhere with Python 3, including a Linux container or
CI runner with no `cmd.exe`:

```sh
python3 tests/static_checks.py
```

They verify that `manifest.json` is valid and that its digests match reality —
including hashing `Cmder.exe` straight out of `lib/cmder-*.zip`, so a stale
manifest is caught without unpacking anything. They also check that `VERSION` is
well-formed, that Cmder is not vendored in the tree, that every `goto` / `call`
target exists, that parentheses balance, that no script still references the
removed download path, and that no file hardcodes a release version.

**Runtime tests** — need Windows:

```bat
tests\run.cmd
tests\run.cmd paths
```

Each case copies the distribution into a temporary folder with a deliberately
awkward path and asserts on the result. The staged copy is built the way
`SETUP.cmd` builds it — source files plus Cmder unpacked from the archive — so
the tests exercise the real flow. Covered: fresh install, reinstall, missing
`nvm.exe`, tampered `nvm.exe`, a tampered Cmder archive, broken `settings.txt`,
paths containing spaces, parentheses, `!` and 8.3 short names, manifest
parsing, that the installed hook is byte-identical to its source in `src\`, that
`user_profile.cmd` is left untouched, non-interactive install, and that the
bootstrap contains no download path.

The runner never modifies the checkout it lives in.

## 🗂️ Project Layout

| Path | Purpose |
| :--- | :--- |
| `SETUP.cmd` | The entry point: verify, unpack Cmder, install the hook, launch |
| `install.cmd` | Prepare the nvm environment and install a version |
| `doctor.cmd` | Report the state of the installation |
| `pack.cmd` | Build the release archive from a checkout |
| `VERSION` | Single source of truth for the cmder-nvm version |
| `manifest.json` | Pinned artifact versions and SHA-256 digests |
| `lib/manifest.cmd` | The only reader of `VERSION` and `manifest.json` |
| `lib/cmder-<version>.zip` | Cmder, as a verified artifact |
| `lib/oobe/` | Linux backend, sourced by `oobe.sh` |
| `oobe.sh` | Cross-platform entry point; dispatches to Windows or Linux |
| `lib/oobe/detect.sh` | OS, architecture, distro and package manager detection |
| `lib/oobe/download.sh` | Download with a curl → wget → python → package manager fallback |
| `lib/oobe/linux.sh` | Linux bootstrap: nvm-sh install, Node.js install, env file |
| `src/profile.d/cmder-nvm.cmd` | First-run hook, copied into `config/profile.d/` |
| `bin/nvm.exe` | Bundled nvm-windows binary, verified before use |
| `bin/install/node_js.cmd` | Install a Node.js version |
| `bin/use/node.cmd` | Activate an installed Node.js version |
| `tests/static_checks.py` | Platform-independent checks |
| `tests/run.cmd` | Windows runtime tests |

### Generated by setup, not tracked

| Path | Produced by |
| :--- | :--- |
| `Cmder.exe`, `vendor/`, `config/`, `opt/`, `icons/` | `SETUP.cmd`, from `lib/cmder-*.zip` |
| `config/profile.d/cmder-nvm.cmd` | `SETUP.cmd`, from `src/profile.d/` |
| `nodejs/`, `node/`, `bin/settings.txt` | `install.cmd` |
| `.nvm/`, `.oobe-cache/` | `oobe.sh` |
| `cmder-nvm-v*.zip` | `pack.cmd` |
